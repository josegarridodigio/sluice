# Research: cgroup escape, per-cgroup swap, interactivity protection (Sluice)

Date: 2026-11-06. Read-only research. Facts are cited with the source; [INF] marks my inference, [UNV] marks something not verified.

Method note: kernel and systemd sources were read from the upstream main branch (raw files), so line behaviour may differ from the user's 7.0.0 kernel in details. ## 1. Processes escaping a delegated cgroup

### 1.1 Kernel rules for migrating a PID (cgroup v2)

- Kernel doc, "Delegation Containment": a non-root writer must have write access to the target's `cgroup.procs` AND to `cgroup.procs` of the common ancestor of source and destination. "...it can't pull in from or push out to outside the sub-hierarchy." Source: https://raw.githubusercontent.com/torvalds/linux/master/Documentation/admin-guide/cgroup-v2.rst
- Code: `cgroup_procs_write_permission()` in `kernel/cgroup/cgroup.c` finds the common ancestor and calls `cgroup_may_write(com_cgrp)` (an ordinary `inode_permission(MAY_WRITE)` on the ancestor's `cgroup.procs`). If the cgroup2 mount has `nsdelegate` (CGRP_ROOT_NS_DELEGATE), the writer must also be able to see both src and dst from its own cgroup namespace, else -ENOENT. Source: https://raw.githubusercontent.com/torvalds/linux/master/kernel/cgroup/cgroup.c
- No uid-of-target check appears in that function [INF: v2 relies purely on file permission on the common ancestor].
- Consequence: a process that moves ITSELF or is moved by ANOTHER process of the same uid is allowed whenever the common ancestor's `cgroup.procs` is writable by that uid. Under `user@1000.service` (Delegate, subtree owned by the user) every cgroup below it has a user-writable `cgroup.procs`, so ANY same-uid process (including the daemon's own jobs, or the user manager) can move any other same-uid process anywhere inside `user@UID.service`. Delegate=yes on the scope does not stop that; delegation only protects what is OUTSIDE the delegated top.
- Delegate semantics from systemd: "Delegate=" makes systemd stop managing the subtree and "migrate processes across the boundaries of that sub-tree as it deems useful anymore"; but it also says nothing about forbidding others from moving processes out. Source: https://systemd.io/CGROUP_DELEGATION/
- Memory charge does not move with the process: "Migrating a process to a different cgroup doesn't move the memory usages that it instantiated while in the previous cgroup to the new cgroup." (cgroup-v2.rst, Memory Ownership). So an escaped Chromium leaves already-charged pages in the job leaf and charges new allocations to the new scope; the job's `memory.current`/anon drops while real usage persists elsewhere.

### 1.2 Can the systemd user manager move a PID out of a Delegate=yes scope?

Yes. Verified in systemd source (main):
- `bus_unit_method_attach_processes()` (`src/core/dbus-unit.c`): requires the TARGET unit to be delegated ("Process migration not available on non-delegated units."), active, and, if the caller is not root and not the manager's uid, the process must be owned by both the sender uid and the target unit's uid. It never inspects the SOURCE cgroup or whether the source is delegated. Source: https://raw.githubusercontent.com/systemd/systemd/main/src/core/dbus-unit.c
- `unit_attach_pids_to_cgroup()` (`src/core/cgroup.c`) calls `cg_attach(path, pid)`, i.e. writes `cgroup.procs` as the user manager; if it fails with a privilege error in a user instance it retries via the system bus. Source: https://raw.githubusercontent.com/systemd/systemd/main/src/core/cgroup.c
- `StartTransientUnit` for a scope with a `PIDs` property goes through `scope_enter_running()` -> `unit_attach_pids_to_cgroup()`; scope_start checks Delegate only for the new unit, nothing about source cgroups ("No PIDs left to attach to the scope's control group, refusing." only when the set is empty). Source: https://raw.githubusercontent.com/systemd/systemd/main/src/core/scope.c
- So the user manager (uid = user) has write permission on the common ancestor (`user@UID.service` or `app.slice`), and a Delegate=yes scope offers no protection against being a SOURCE.

### 1.3 The Chromium case (primary source)

- Chromium `components/dbus/xdg/systemd.cc` (`SetSystemdScopeUnitNameForXdgPortal`): calls `org.freedesktop.systemd1.Manager.StartTransientUnit` with unit `app-<escaped app name>-<pid>.scope`, mode `replace`, property `PIDs=[own pid]` and `Delegate=true` (comment: "AttachProcessesToUnit() requires a delegated unit."). After it becomes active, `MigrateDescendantsToUnit()` calls `AttachProcessesToUnit` for each descendant (zygotes, GPU process, renderers) in up to 3 breadth-first passes. Source: https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/dbus/xdg/systemd.cc
- Skip conditions found in the code: running under Flatpak/Snap (app sandbox != none); no owner of `org.freedesktop.systemd1` on the bus it connects to (`kNoSystemdService`); pid <= 1; StartTransientUnit failure. No feature flag, no env var, no "already in a scope" check was visible. The comment cites an xdg-desktop-portal use ("SetSystemdScopeUnitNameForXdgPortal").
- [INF] Practical ways to keep Chromium in the leaf: make the session bus unreachable for the job (unset `DBUS_SESSION_BUS_ADDRESS`, do not bind the user bus socket in the job's mount namespace) so the NameHasOwner check fails, or run the job in its own mount namespace with a private/dummy bus. [UNV] whether Chromium falls back to the default `$XDG_RUNTIME_DIR/bus` path when the env var is unset (libdbus does this by default on Linux; it needs testing).
- Chromium also had earlier discussion: a Red Hat RFE asks for per-renderer cgroups because one scope shares all processes: https://bugzilla.redhat.com/show_bug.cgi?id=1931938

GNOME Shell itself also moves launched apps into `app-*.scope` via the same mechanism (Launchpad bug text: https://bugs.launchpad.net/ubuntu/+source/kio/+bug/2011806/comments/13); jobs launched by the daemon do not go through the shell.

### 1.5 Does `CLONE_NEWCGROUP` (unshare --cgroup) stop it?

- Kernel doc, nsdelegate: "Consider cgroup namespaces as delegation boundaries." A process inside the namespace cannot see or write cgroups outside its namespace root; migrations require both ends reachable from the WRITER's namespace (-ENOENT otherwise). Source: cgroup-v2.rst and `cgroup_procs_write_permission` above. systemd mounts cgroup2 with `nsdelegate,memory_recursiveprot` (verified in `src/shared/mount-setup.c`, and `mount` on the user's machine shows nsdelegate,memory_recursiveprot).
- It does stop the namespaced process from moving ITSELF or others out (it cannot name a cgroup above its root; `/proc/PID/cgroup` shows paths relative to the root). It does NOT stop systemd: the user manager runs in the root namespace and can see everything, and Chromium's escape is a D-Bus request executed by the user manager, not a write by Chromium. [INF] So `unshare --cgroup` alone does not prevent the Chromium escape unless the bus is also unreachable. It does help against direct-write escapes by sandboxed tools.
- [INF] The PID namespace (`CLONE_NEWPID`) combined with a bus-less mount namespace makes the AttachProcessesToUnit route harder: the pid Chromium sends is namespace-translated by the bus credentials; [UNV] interplay not tested.

### 1.6 Detection and reclamation by a supervisor

- `cgroup.events` `populated` only changes when the subtree becomes empty or non-empty; a single process leaving a still-populated cgroup produces NO notification (cgroup-v2.rst "cgroup.events": "poll and [id]notify events are triggered when the value changes").
- `cgroup.kill`: "kills all processes in the cgroup tree... deals with concurrent forks and is protected against migrations", but only for processes currently inside. Escaped processes are untouched. Source: cgroup-v2.rst. kernel patch notes it ignores PID namespaces: https://lore.kernel.org/all/m1v97x6niq.fsf@fess.ebiederm.org/T/
- Process connector (`cn_proc`): joining the netlink multicast group requires `ns_capable(net->user_ns, CAP_NET_ADMIN)` (`drivers/connector/connector.c`, line ~176), so an unprivileged user daemon cannot use it [INF from the capability check; the user-namespace variant is not explored].
- `PR_SET_CHILD_SUBREAPER` makes orphaned descendants reparent to the supervisor so it can walk the process tree; processes that daemonize still reparent to it. It tracks lineage independent of cgroups, so a moved process stays tracked [INF; standard prctl behaviour, not re-verified against kernel docs here]. `pidfd_open` gives race-free handles per descendant, but discovery of new children still needs polling `/proc/<pid>/task/*/children` or the subreaper plus `waitid`.
- Cheap polling alternative: each tick, for each job read `/proc/<pid>/cgroup` for the job's known process set and flag mismatches (this is exactly what Chromium's own migration code does: "descendant processes whose cgroup differs from the original").
- Moving back: write the PID to `<job leaf>/cgroup.procs`. Allowed when the writer has write on the common ancestor's `cgroup.procs`. The escaped scope (`app.slice/app-chromium-N.scope`) and the job leaf share an ancestor inside `user@UID.service`, which the daemon (same uid) can write. In the user's setup the daemon is itself inside `sluice-daemon.scope` under the user manager, so this should work [INF, not tested]. Caveats: (a) Chromium ran its own migration with a 3-pass scan and may re-migrate children; (b) systemd's scope `app-chromium-N.scope` then becomes empty and is stopped, and the PID's pages already charged to the new scope stay charged there; (c) systemd `cg_attach` writes would race with the daemon's writes.
- Systemd option: `systemctl --user` can set `Delegate=` and the unit owns the cgroup; if jobs were run as `systemd-run --user --scope/--slice`, then Chromium's `replace`-mode StartTransientUnit would still move it (nothing prevents it).

## 2. Swap per cgroup

### 2.1 Interface semantics (kernel doc)

- `memory.swap.max`: "Swap usage hard limit. If a cgroup's swap usage reaches this limit, anonymous memory of the cgroup will not be swapped out." Meta's doc adds that pages already holding swap slots can still be swapped out: https://facebookmicrosites.github.io/cgroup2/docs/memory-controller.html
- `memory.swap.high`: "point of no return"; allocations are throttled once swap usage exceeds it "to allow userspace to implement custom out-of-memory procedures"; "NOT designed to manage the amount of swapping a workload does during regular operation." Healthy workloads are not expected to reach it.
- `memory.swap.events`: `high`, `max`, `fail` counters; reducing swap.max below usage reclaims swap entries "gradually".
- `memory.zswap.max`: when the cgroup's zswap pool reaches the limit, it "will refuse to take any more stores before existing entries fault back in or are written out to disk"; `memory.zswap.writeback=0` disables all swap-device writes (including zswap writeback) for the cgroup and may cause reclaim inefficiency with incompressible pages (hierarchical).
- `memory.max`: "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup." `memory.high`: throttles and puts the cgroup under heavy reclaim, "never invokes the OOM killer"; docs recommend an external agent monitors a cgroup held at `high`. The kernel doc itself calls memory.high "the main mechanism to control memory usage" and says the monitoring agent needs a pressure measure (memory pressure monitoring "isn't implemented yet" is stale text in the Usage Guidelines section, since PSI exists).
- Source for all: https://raw.githubusercontent.com/torvalds/linux/master/Documentation/admin-guide/cgroup-v2.rst

### 2.2 What happens at memory.max with swap allowed vs swap.max=0

- With swap allowed, charging beyond `memory.max` triggers direct reclaim inside the cgroup: file pages first by default; anon pages are swapped out according to swappiness, until the limit is satisfied. The allocating task stalls in reclaim; if reclaim fails repeatedly, memcg OOM. So a job continually pushed against a `memory.max` smaller than its working set swaps its own hot anon pages out and back in (thrash), without ever reaching an OOM, for as long as swap has room.
- With `memory.swap.max=0`, anon pages cannot be swapped; only file pages are reclaimable, so a job whose anon exceeds `memory.max` gets OOM-killed fast ("no swap without headroom turns slow failure into fast OOM": https://velobot-wiki.pages.dev/article/software/linux-cgroup-v2-memory-controller-playbook/ , secondary source, unattributed wiki). Meta used `memory.swap.max=0` for its latency-sensitive workload slice and let `system.slice` use swap: https://facebookmicrosites.github.io/cgroup2/docs/memory-controller.html
- Kernel commit "mm, memcg: throttle allocators when failing reclaim over memory.high": the problem is worst "when no swap is configured or swap is full"; containment can fail entirely and cause OOM outside the cgroup: https://git.zx2c4.com/linux-dev/commit/kernel?id=0e4b01df865935007bd712cbc8e7299005b28894 (the quoted failure mode is also at https://www.mail-archive.com/linux-kernel@vger.kernel.org/msg1975282.html, where memory.pressure rose to 98.5% while a job kept running at 110% of memory.high).

### 2.3 Interaction with global reclaim and other cgroups

- Reclaim triggered by a cgroup limit (memory.max / memory.high) targets that cgroup's own LRUs (and descendants). It does not scan siblings; `memory.low` of siblings is irrelevant to it. cgroup-v2.rst "Reclaim Protection": "The protection ... applies relatively to the target of the reclaim (i.e. any of memory cgroup limits, proactive memory.reclaim or global reclaim apparently located in the root cgroup)". [INF] Therefore in the incident, where MemAvailable stayed >= ~8 GiB (so global reclaim/kswapd was not the driver), the swap-out was the job cgroups' own reclaim at `memory.max`, and the shell's pages were not the victims of that reclaim. The shell was starved by SHARED resources, not by being reclaimed by the job's limit (see 2.4).
- Swap I/O accounting: the cgroup v2 io controller attributes swap I/O to the cgroup that owns the page; io.latency avoids throttling swap/metadata I/O directly (priority inversion) and instead "back-charges" the owner with a delay on return to userspace: https://lwn.net/Articles/758697/ . [INF] Without the `io` controller delegated, no I/O isolation is possible for the user: the user manager's `user@.service` has `Delegate=pids memory cpu` (no `io`) in `units/user@.service.in` upstream: https://raw.githubusercontent.com/systemd/systemd/main/units/user@.service.in
- Chris Down: "Swap is not what makes your application slow – entering overall memory contention is what makes your application slow", "Swap is primarily a mechanism for equality of reclamation", and swap can make a system slower to OOM-kill; disabling swap just moves thrash to file pages: https://chrisdown.name/2018/01/02/in-defence-of-swap.html (opinion by a Meta kernel engineer, not data).

### 2.4 Does a cgroup held at memory.max, swapping heavily, degrade the rest of the machine? Evidence

- No benchmark data found for exactly this scenario. Mechanisms documented: (1) shared swap device bandwidth/latency (all I/O queues share the device; the io controller can only isolate if enabled and delegated); (2) CPU burned in reclaim by the job's tasks (cgroup-local, but still CPU); (3) PSI: memory pressure is tracked per cgroup AND system-wide; tasks stalled in cgroup reclaim count as memory-stalled in the system-wide file, so `/proc/pressure/memory` rises even though only the job is being reclaimed [INF: psi accounts per-task stall to every cgroup ancestor and the root].
- The one real-world desktop write-up found (Arch, 8 GB + 4 GB swap, kernel 6.18.5) blames thrashing of executable pages of UI processes: "executable pages of important programs that process the UI are constantly unloaded and reloaded"; its fix was MGLRU `min_ttl_ms=1000`: https://link2xt.codeberg.page/blog/2026-01-23-linux-out-of-memory.html (single source, desktop under global memory shortage, not cgroup-limited).
- Consequence for Sluice [INF, to be tested]: because the job leaf's reclaim doesn't touch gnome-shell, a hang with MemAvailable >= 8 GiB points to swap I/O saturation (page faults of the compositor on file/exec pages or its swapped anon pages queue behind swap writes of 1,700 pages/s) and/or CPU contention, rather than direct eviction of the shell. Metrics to capture in a repro: `/proc/pressure/io` full, `/proc/pressure/memory`, `io.stat` of the swap device, per-cgroup `memory.pressure` of the shell's scope vs job leaves, `memory.stat pswpout/pswpin`, and the swap device type (rotational/NVMe).

## 3. Protecting interactivity

### 3.1 memory.low / memory.min

- Semantics (cgroup-v2.rst): `memory.min` hard, never reclaimed ("If there is no unprotected reclaimable memory available, OOM killer is invoked"); `memory.low` best effort, not reclaimed unless unprotected cgroups have nothing reclaimable. Effective protection is capped by every ancestor's value: "Effective low boundary is limited by memory.low values of ancestor cgroups"; overcommit is split proportionally to usage.
- Mount options: with `memory_recursiveprot` (set by systemd, see 1.5), protection on a parent applies recursively to the subtree without writing leaf values.
- Who may write: ordinary file permission on `memory.low`/`memory.min`; the delegatee "shouldn't be allowed to write" the resource files of the delegated top cgroup (kernel doc, Delegation). A user manager owns `user@UID.service/...`; it can set `MemoryLow=` on units within its own subtree (for example `session.slice`/`app.slice` children, including the shell's units), but protection of `user@UID.service` as a whole against system-wide reclaim needs a value on `user@UID.service`/`user.slice`, which only the system manager (root) can write. Because effective protection is capped by ancestors, user-level `memory.low` for the shell is only effective against reclaim whose target is `user@UID.service` or above if the ancestors carry protection. [INF] But for a job's own `memory.max` reclaim, the target is the job leaf, so sibling protection is irrelevant (see 2.3).
- Meta (fbtax2): used `memory.low` on `workload.slice` instead of capping `system.slice` with `memory.high`, because capping system binaries made them thrash and OOM: https://facebookmicrosites.github.io/cgroup2/docs/memory-controller.html

### 3.2 PSI-based controllers

- Kernel PSI doc: some/full definitions, `avg10/60/300` and `total` (us); trigger syntax `"some 150000 1000000"` = 150 ms of partial stall in a 1 s window; window 500 ms - 10 s; unprivileged triggers need a window multiple of 2 s; one trigger per fd (open the file separately; second write gives EBUSY); notifications are rate-limited to one per window; per-cgroup `memory.pressure` supports the same triggers ("Per-cgroup psi monitors can be specified and used the same way as system-wide ones"). Source: https://raw.githubusercontent.com/torvalds/linux/master/Documentation/accounting/psi.rst . Note `cgroup.pressure` can disable PSI per cgroup (cgroup-v2.rst).
- Weiner on the averages: they "identify persistent long-term trends and very clear and obvious overloads, but it's unusable for latency spikes"; use the cumulative `total` for spikes: https://lkml.iu.edu/hypermail/linux/kernel/1807.2/03585.html (also lore thread https://lore.kernel.org/lkml/20180913014923.GB2370@cmpxchg.org/T/ ).
- systemd-oomd: defaults in `src/oom/oomd.conf`: `SwapUsedLimit=90%`, `DefaultMemoryPressureLimit=60%`, `DefaultMemoryPressureDurationSec=30s`. It uses the FULL line of the cgroup's `memory.pressure`, `avg10` (code: `read_resource_pressure(p, PRESSURE_TYPE_FULL, ...)` in `src/oom/oomd-util.c`, comparison `memory_pressure.avg10 > mem_pressure_limit`). Only descendants of units with `ManagedOOMMemoryPressure=kill` are candidates; leaf cgroups or `memory.oom.group=1`. Sources: https://raw.githubusercontent.com/systemd/systemd/main/src/oom/oomd.conf ; https://raw.githubusercontent.com/systemd/systemd/main/src/oom/oomd-util.c ; https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html
- Fedora enabled it with `ManagedOOMMemoryPressureLimit=50%` for 20 s on `user@.service` and `SwapUsedLimit=90%`, noting that apps need separate cgroups for it to act; it also argues PSI actions track memory protection better than raw usage: https://fedoraproject.org/wiki/Changes/EnableSystemdOomd . Desktop complaints: it kills the whole shell/terminal scope under load: https://bugs.launchpad.net/bugs/1985887 ; https://lists.ubuntu.com/archives/ubuntu-devel/2022-June/042116.html
- Meta oomd: plugins `pressure_above resource=memory threshold=60 duration=30` ("CONTINUE if 10s pressure > threshold longer than duration") and `swap_free threshold_pct=10`; the doc gives example, not recommended, values: https://raw.githubusercontent.com/facebookincubator/oomd/main/docs/core_plugins.md . Meta credits oomd as what makes swap workable: https://facebookmicrosites.github.io/cgroup2/docs/memory-controller.html
- senpai (Meta): feedback loop that adjusts `memory.high` of a container from its PSI to find the working set; example config `interval=5`, `pressure=1000` (units not stated in the README), `max_probe=0.01`, `max_backoff=0.1`: https://raw.githubusercontent.com/facebookincubator/senpai/main/README.md . (Details of the algorithm not documented in the README.)
- Android lmkd: PSI window 1000 ms (`PSI_WINDOW_SIZE_MS`); partial stall threshold default 70 ms (200 ms on low-RAM devices) per 1 s window, complete stall 700 ms (kill levels medium/critical); also swap-free and thrashing limits: https://android.googlesource.com/platform/system/memory/lmkd/+/refs/heads/main/lmkd.cpp (macros `DEF_PARTIAL_STALL=70`, `DEF_PARTIAL_STALL_LOWRAM=200`, `DEF_COMPLETE_STALL=700`).
- psi-notify (desktop notifier) default memory trigger `some avg10 10.00` (via search-result snippet of its man page, https://manpath.be/f38/1/psi-notify, not independently read) [UNV].
- No authoritative number for "interactive degradation" exists. Evidence range: lmkd 7% partial stall per 1 s window = mobile UI jank; psi-notify 10% some avg10 = warning; systemd-oomd 50-60% full avg10 for 20-30 s = kill. [INF] A throttle signal for a job supervisor would sit near the lmkd/psi-notify end (some avg10 of ~5-10% sustained, or a trigger of ~70-150 ms per 1 s window), not near the oomd kill level.

### 3.3 Can a job supervisor read the session's memory.pressure as an admission/throttle signal?

- Reading is allowed: `memory.pressure` is world-readable in the cgroup tree (systemd docs: "You may read" systemd-created cgroup files, https://systemd.io/CGROUP_DELEGATION/). [INF] The user can read `user@UID.service/memory.pressure`, `app.slice/.../memory.pressure` and the shell's scope. PSI triggers need an fd opened O_RDWR on the file: writing a trigger to a file one does not have write permission for would fail with EACCES, so triggers on the session slice may not be creatable by the user for files owned by root-managed cgroups [UNV: file mode of `memory.pressure` is 0644 root-owned for system-created cgroups; the kernel allows an unprivileged trigger on files the user can open for writing. Needs testing]. Polling the file each second and reading `avg10` or the `total` delta works without writes.
- `/proc/pressure/memory` (system-wide) is readable by everyone; it requires no cgroup permission. Pressure of the SESSION cgroup includes the jobs' own stalls (they are descendants if they live in `user@UID.service`), so the signal is self-referential; to separate "jobs are stalled" from "shell is stalled" compare pressure of the shell's own cgroup vs. the jobs' cgroup [INF].
- Which line: `some` is the earlier, more sensitive signal (at least one task stalled); `full` means all non-idle tasks stalled. systemd-oomd uses `full avg10`.

## 4. GNOME Shell / mutter hangs after heavy swap

- GNOME GitLab gnome-shell #2884: gnome-shell RSS grows until swap is full and the system "freezes with disk I/O" (GNOME 3.36, Xorg). Root cause there is a shell leak, not external swap pressure, but it shows the symptom (freeze with disk I/O) reported to the project: https://gitlab.gnome.org/GNOME/gnome-shell/-/issues/2884
- GNOME GitLab mutter #2431 (Wayland, Ubuntu 22.04, mutter 42.4): under `stress-ng --stack` memory stress, "screen freeze, the mutter is waiting for syncobj" (DRM_IOCTL_SYNCOBJ_WAIT); kernel trace through swap-in paths (`swap_cluster_readahead`, `shmem_swapin`); freeze tends to follow a second "gnome-shell: page allocation failure: order:0"; the report has no developer response in the page content: https://gitlab.gnome.org/GNOME/mutter/-/issues/2431 . This is a hang (not just lag), but it involves allocation failure (near-OOM), so it is not equivalent to the incident where MemAvailable stayed high.
- Forum evidence for hang rather than lag: V2EX thread (Chinese) says desktop "freezes" when RAM+swap is exhausted and Alt+F2 `r` may not even work because GNOME owns the compositor: https://v2ex.com/t/751883 (single source, forum anecdote). NixOS Discourse (GNOME 45 on X11, CPU-heavy builds, swap nearly full): everything stalls while pages are evicted and reloaded: https://discourse.nixos.org/t/desktop-often-freezes-during-cpu-intense-tasks/41583 . Arch write-up above (keyboard shortcuts and cursor stop responding for a long time, sometimes a hard reset): https://link2xt.codeberg.page/blog/2026-01-23-linux-out-of-memory.html
- No gitlab.gnome.org issue found that documents "heavy swap-out by a different cgroup with free RAM left" hanging mutter. I could not find a GNOME-developer statement on a root cause; the hang evidence is therefore indirect (thrashing of shell exec/file pages and swap I/O contention).
- Fedora's systemd-oomd change and the Ubuntu bug lists show the opposite problem (oomd killing gnome-shell) rather than hangs; see 3.2.

## Implications for a job supervisor in a delegated user cgroup

1. Lower the swapping the job itself can do: set `memory.swap.max` per job leaf, either 0 or a small fraction (a few percent of RAM). With `memory.max` = anon + share, a job above its limit then fails fast (OOM inside the leaf, recoverable by the supervisor: retry later) instead of grinding in the swap device for minutes. This follows Meta's use of `memory.swap.max=0` for latency-sensitive workloads. Trade-off: more OOM kills on spikes; 0 is only safe if the memory estimate is honest.
2. A graded alternative: `memory.swap.high` is NOT meant for regular operation, so do not use it for steady-state throttling; `memory.high` slightly below `memory.max` (the kernel docs' "main mechanism") with an external agent watching PSI is the designed pattern, but it still swaps unless `swap.max` is small.
3. Do not use the first symptom (swap size) as the trigger: use rates and pressure. Candidate signals the supervisor can read without privilege: `pswpout`/`pswpin` deltas in `memory.stat` per job and in `/proc/vmstat`, `/proc/pressure/memory` and `/proc/pressure/io` (`some` avg10 and `total` deltas), per-leaf `memory.pressure`, `memory.events` (`high`, `max`, `oom`), `memory.swap.events`. The incident's 1,700 pages/s out is about 6.6 MiB/s of 4 KiB pages, which is small for NVMe; if the hang was real, suspect read amplification/latency (swap-ins, shell page faults) or CPU stalls rather than bandwidth [INF; verify with the I/O PSI numbers in a repro].
4. Use the shell cgroup's own PSI as the interactivity probe: read `memory.pressure` and `io.pressure` of the cgroup holding gnome-shell (and system-wide `/proc/pressure/{memory,io}`), poll each second, throttle admission when `some avg10` stays above ~5-10% (starting point from lmkd/psi-notify; tune empirically) and cut `memory.max` of the heaviest job when pressure persists, instead of waiting for kill-level values (oomd's 50-60% full). Reading is permitted; creating PSI triggers on cgroups the user does not own may not be [UNV].
5. Protection from the user side is limited: the user may set `MemoryLow=` on units inside `user@UID.service`, but effective low is capped by ancestors and the global protection of `user@UID.service`/`user.slice` needs root. A one-time system-level drop-in (`MemoryLow=` on `user@.service`, plus optional swap handling) is a documented install-time option for the product; it cannot be done by the daemon itself. Job-limit reclaim (`memory.max`) never targets siblings, so sibling `memory.low` does not help in the observed scenario.
6. I/O isolation is not available to the user (`io` is not delegated to `user@.service` by default). Options: ask for `Delegate=io`/`IOWeight` at system level, or reduce swap I/O at the source (point 1).
7. Escape handling: (a) prevent: run jobs with no reachable session bus (unset `DBUS_SESSION_BUS_ADDRESS`, no user bus socket in the job mount namespace) so Chromium's `NameHasOwner(org.freedesktop.systemd1)` check fails; optionally `unshare --cgroup --pid --mount` as defence in depth against direct writes; (b) detect: each second compare `/proc/<pid>/cgroup` of all known descendants (kept via `PR_SET_CHILD_SUBREAPER` and pidfds) with the job leaf path; do not rely on `cgroup.events` (it will not fire) or `cn_proc` (needs CAP_NET_ADMIN); (c) reclaim: write the PID back to the job leaf's `cgroup.procs` (allowed for the same uid inside `user@UID.service`), accepting that already-charged memory stays in the scope and that Chromium may re-migrate; (d) fall back to killing by PID tree/subreaper walk for escaped processes, since `cgroup.kill` cannot reach them; (e) account for escaped processes' memory by summing their `/proc/<pid>/smaps_rollup` or reading the new scope's `memory.current` and attributing it to the job.
8. Account escaped anon in the allowance formula: if the job's `memory.current` falls while the machine's MemAvailable does not, treat the delta as an escape signal.
9. Test plan before adopting (not done here, read-only constraint): (i) reproduce with a synthetic job at `memory.max` below its working set with swap allowed and record IO/memory PSI and shell stalls; (ii) repeat with `memory.swap.max=0`; (iii) verify the `DBUS_SESSION_BUS_ADDRESS` unset does keep Chromium in the leaf; (iv) verify the write-back of a PID to the leaf from the daemon.

## Uncertainties summary

- Causality of the compositor hang (I/O vs CPU vs page-fault stalls) is unproven; all of 2.3/2.4 mechanism statements about it are inference.
- Whether Chromium falls back to the default user-bus path when the env var is unset is untested.
- User write access to `memory.pressure` for PSI triggers on session cgroups is unverified.
- Exact permission behaviour of "move back" across `app.slice/app-*.scope` is derived from the kernel permission function, not tested.
- Kubernetes LimitedSwap formula, Nix `cgroup.kill` use, BuildKit specifics: not verified.
