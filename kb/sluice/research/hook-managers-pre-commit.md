# Hook managers: pre-commit v4.7.0

Source analysis of pre-commit **v4.7.0** (`<repo>/refs/pre-commit`; the
CHANGELOG's top entry is `4.7.0 - 2026-10-12`, `CHANGELOG.md:1`). Nothing was
installed or run: every claim is read from the code. `file:line` references are
relative to the pre-commit checkout (`pre_commit/...`) unless prefixed with
`sluice:`. Anything that the code does not prove is marked **(inference)**.
Companion of `hook-managers-husky.md`.

pre-commit is a Python program. It is not a hook file: the hook installed in
`.git/hooks` is a 20-line bash stub that `exec`s the Python program, which reads
`.pre-commit-config.yaml`, selects hooks, and runs them. The runner logic is
therefore in the config interpreter, not in the installed file.

## 1. Install mechanics

### 1.1 What `pre-commit install` writes

`install()` (`commands/install_uninstall.py:114-141`):

1. `git_dir is None and git.has_core_hookpaths_set()` -> logs the refusal and
   returns 1 (`:123-128`, exact text below, section 1.3).
2. For each hook type in `_hook_types()` (`:35-44`): the `-t/--hook-type` values
   if given; otherwise the config's `default_install_hook_types`
   (schema default `['pre-commit']`, `clientlib.py:507-511`); if the config does
   not load (`InvalidConfigError`) it silently falls back to `['pre-commit']`.
   Valid types: `commit-msg post-checkout post-commit post-merge post-rewrite
   pre-commit pre-merge-commit pre-push pre-rebase prepare-commit-msg`
   (`clientlib.py:26-37`). `manual` is a stage only, never installed (`:38-39`).
3. `_install_hook_script()` writes one file per type (`:64-111`).
4. `--install-hooks` additionally builds every environment of the config
   (`:138-139`, `:144-146`).

**Where**: `<git-common-dir>/hooks/<hook-type>` (`_hook_paths`, `:47-53`, using
`git rev-parse --git-common-dir`, `git.py:86-93`). It never consults
`core.hooksPath` to choose the directory, because it refuses to run when that is
set. `--git-common-dir` means linked worktrees share the main repository's
hooks directory; there is an explicit worktree test
(`tests/commands/install_uninstall_test.py:190-202`).

**What** (template `resources/hook-tmpl`, 20 lines):

```bash
#!/usr/bin/env bash
# File generated by pre-commit: https://pre-commit.com
# ID: 138fd403232d2ddd5efb44317e38bf03
# start templated
INSTALL_PYTHON='<abs path of the python that ran `pre-commit install`>'
ARGS=(hook-impl --config=<cfg> --hook-type=<type> [--skip-on-missing-config])
# end templated
HERE="$(cd "$(dirname "$0")" && pwd)"
ARGS+=(--hook-dir "$HERE" -- "$@")
if [ -x "$INSTALL_PYTHON" ]; then exec "$INSTALL_PYTHON" -mpre_commit "${ARGS[@]}"
elif command -v pre-commit > /dev/null; then exec pre-commit "${ARGS[@]}"
else echo '`pre-commit` not found.  Did you forget to activate your virtualenv?' 1>&2; exit 1; fi
```

(`resources/hook-tmpl:1-20`; the templated block is filled at
`install_uninstall.py:104-108`.) On win32 a `#!/bin/sh` line is prepended
(`:101-102`).

- **Locating the Python / executable**: `INSTALL_PYTHON` is `sys.executable` of
  the interpreter that executed `install` (`:105`, quoted with `shlex.quote`).
  At hook time, if that path is still executable it is used
  (`python -mpre_commit`); otherwise `pre-commit` on `PATH`; otherwise exit 1
  with the message above (`hook-tmpl:13-20`). A deleted virtualenv therefore
  degrades to the `PATH` lookup.
- **Locating the config**: it is *not* discovered at hook time. `--config=<cfg>`
  is baked into the script (`:88`); the value is the path the user passed to
  `install -c` (default `.pre-commit-config.yaml`, `main.py:50-55`), made
  relative to the repository root (`main.py:188-191`). `hook-impl` then
  `chdir`s to the repository root (`main.py:188-189`; `hook-impl` is not in
  `COMMANDS_NO_GIT`, `main.py:44-47`).
- The file is recognised as pre-commit's by a content hash: `is_our_script`
  looks for `CURRENT_HASH` or any of five `PRIOR_HASHES` anywhere in the file
  (`:23-30`, `:56-61`). Installing again over its own script just rewrites it
  (`:92`).

### 1.2 `--hook-type`, `--overwrite`, legacy chaining

- `-t/--hook-type` is repeatable (`main.py:57-61`).
- **Legacy chaining**: if a hook file exists at the target and is not ours, it is
  *moved* to `<hook>.legacy` (`:75-77`) and the user is told "Running in
  migration mode with existing hooks at ..." (`:82-86`). At run time the stub
  passes `--hook-dir "$HERE"`, and `hook_impl._run_legacy` executes
  `<hook-dir>/<hook-type>.legacy` first if it is executable, with the same
  arguments, with the pre-push stdin forwarded (`hook_impl.py:31-46`) and with
  `PRE_COMMIT_RUNNING_LEGACY=1` in its environment (`:44`). Its return code is
  `retv`, OR-ed with pre-commit's own result (`:269-275`). The legacy hook runs
  **before** the config is even validated (`:269-270`).
- `-f/--overwrite` deletes an existing `.legacy` file instead of chaining
  (`:79-81`); it is also the flag that "removes migration mode"
  (`main.py:275-278`).
- If the stub is somehow found as its own legacy, `_run_legacy` aborts with
  "bug: pre-commit's script is installed in migration mode" when
  `PRE_COMMIT_RUNNING_LEGACY` is already set (`hook_impl.py:22-29`): this is the
  recursion guard.
- `uninstall` removes the hook only if it is ours and then moves `.legacy` back
  into place (`:149-161`).
- **Direct-use mode**: `--hook-dir` is optional; when absent `_run_legacy`
  returns immediately (`hook_impl.py:36-37`). CHANGELOG 4.6.0: "allow
  `--hook-dir` to be missing to enable easier usage with `git` 2.54+ git hooks"
  (`CHANGELOG.md:41-46`). So `pre-commit hook-impl --config=<cfg>
  --hook-type=<type> -- <git hook args>` is a supported, documented-in-code way
  to invoke exactly what the installed stub invokes, without the stub and
  without legacy chaining.

### 1.3 `core.hooksPath` refusal

Exact logic: `git config core.hooksPath` run without a scope flag (so it sees
system, global and local config merged); any non-empty output counts
(`git.py:180-182`). `install` is refused when `git_dir is None` (the normal,
non-template case):

```
Cowardly refusing to install hooks with `core.hooksPath` set.
hint: `git config --unset-all core.hooksPath`
```

and exits 1 (`install_uninstall.py:123-128`). Consequences (all read from the
code):

- A **local** `core.hooksPath` pointing at Sluice's directory makes
  `pre-commit install` fail. So does a **global** one.
- `uninstall` and `hook-impl`/`run` do not check the setting (no reference in
  `main.py`, `run.py`, `hook_impl.py`); `uninstall` computes its path from
  `--git-common-dir` and ignores `core.hooksPath` (`:149-153`).
- When git uses a `core.hooksPath`, git never runs `.git/hooks/*`, so a
  previously installed pre-commit stub is dead code **(inference: git
  behaviour, not in this repository)**.

### 1.4 `init-templatedir`

`pre-commit init-templatedir <dir>` calls `install(... overwrite=True,
skip_on_missing_config=True, git_dir=<dir>)` (`commands/init_templatedir.py:14-28`),
writing `<dir>/hooks/<type>`. Passing `git_dir` bypasses the `core.hooksPath`
refusal (`install_uninstall.py:123`). The stubs carry
`--skip-on-missing-config` so that clones of repositories without a config do
not fail (`hook_impl.py:49-67`; `init-templatedir` defaults to allowing a missing
config, `main.py:265-270`). It only warns when
`git config init.templateDir` does not equal the directory
(`init_templatedir.py:29-38`). `init-templatedir` is in `COMMANDS_NO_GIT`
(`main.py:44-47`) so it works outside a repository.

## 2. Runtime flow (`hook-impl`)

Entry: `main.py:400-409` -> `hook_impl()` (`hook_impl.py:259-275`):

```
retv, stdin = _run_legacy(...)          # legacy hook first
_validate_config(retv, config, skip)    # missing config handling
ns = _run_ns(hook_type, color, args, stdin)
return retv if ns is None else retv | run(config, store, ns)
```

### 2.1 Missing config, `PRE_COMMIT_ALLOW_NO_CONFIG`

`_validate_config` (`hook_impl.py:49-67`): if the config file does not exist and
either `--skip-on-missing-config` was baked in or env
`PRE_COMMIT_ALLOW_NO_CONFIG` is set, it prints "`<cfg>` config file not found.
Skipping `pre-commit`." and exits with the legacy hook's `retv`; otherwise
prints the three-line explanation and exits 1.

### 2.2 Arguments per hook type

`_check_args_length` (`:177-211`) enforces the argument counts git passes:
`commit-msg` 1, `post-checkout` 3, `post-commit` 0, `pre-commit` 0,
`pre-merge-commit` 0, `post-merge` 1, `post-rewrite` 1, `pre-push` 2,
`prepare-commit-msg` 1-3, `pre-rebase` 1-2. `_run_ns` (`:214-256`) maps them to
the `run` namespace:

| git hook | mapping | file source in `run` |
|---|---|---|
| pre-commit, pre-merge-commit, post-commit | no refs | staged files (or conflicted files, or none) |
| commit-msg | `commit_msg_filename=args[0]` (`:224`) | `(commit_msg_filename,)` (`run.py:260-261`) |
| prepare-commit-msg | filename, optional source, optional commit object (`:225-236`) | same |
| post-checkout | `from_ref=args[0], to_ref=args[1], checkout_type=args[2]` (`:239-243`) | none |
| post-merge, post-rewrite, pre-rebase | flags/upstream/branch | none (`run.py:255-259`) |
| pre-push | see 2.3 | `git diff --name-only from...to` or all files |

### 2.3 pre-push: stdin refs -> from/to

`_pre_push_ns` (`:120-174`): `args[0]` is the remote name, `args[1]` the URL; the
stdin lines are `local_branch local_sha remote_branch remote_sha`
(`rsplit(maxsplit=3)`, `:128-130`).

- `local_sha == Z40` (a branch deletion) -> that line is skipped (`:131-132`);
  `Z40 = '0'*40` is hard-coded (`:14`) **(inference: a SHA-256 repository would
  not match this sentinel)**.
- `remote_sha` non-zero and the commit exists locally -> `from_ref=remote_sha,
  to_ref=local_sha` (`:133-140`).
- Otherwise (new branch or unknown remote commit): `git rev-list local_sha
  --topo-order --reverse --not --remotes=<remote_name>` (`:143-146`). No
  ancestors -> skip the line. If the first ancestor is a root commit
  -> `all_files=True` (`:150-161`); else `from_ref=<first_ancestor>^`,
  `to_ref=local_sha` (`:162-171`).
- **Only the first line that produces a namespace is used**: every branch
  `return`s inside the loop (`:134,155,165`); later ref lines of a multi-ref
  push are ignored. If nothing qualifies the function returns `None`, and
  `hook_impl` returns `retv` without running any hook (`:172-174`, `:272-273`).
- The remote name/URL/branches are exported to the hooks as
  `PRE_COMMIT_REMOTE_NAME/URL`, `PRE_COMMIT_LOCAL_BRANCH`,
  `PRE_COMMIT_REMOTE_BRANCH` (`run.py:398-405`).

### 2.4 `run()`: pre-flight checks, environment, stash

`commands/run.py:338-445`:

- `stash = not args.all_files and not args.files` (`:344`). So the stash is
  active for every git-hook invocation (including pre-push and commit-msg,
  which set neither) **and** for `pre-commit run --from-ref/--to-ref`.
- With `stash`: unmerged paths -> "Unmerged files.  Resolve before committing."
  exit 1 (`:347-349`, `:325-327`); a config file with unstaged modifications
  (`git diff --quiet <config>` == 1) -> "Your pre-commit configuration is
  unstaged." exit 1 (`:353-358`, `:330-335`).
- `--from-ref` without `--to-ref` (or vice versa) -> exit 1 (`:350-352`).
- `commit-msg`/`prepare-commit-msg` require `--commit-msg-filename`
  (`:359-367`).
- Recursion guard: `post-checkout` returns 0 when
  `_PRE_COMMIT_SKIP_POST_CHECKOUT` is set (`:369-373`), which is set by the
  stash's own `git checkout` (`staged_files_only.py:77-81`).
- Environment exported to hooks (mutating `os.environ`, inherited by hook
  subprocesses): `PRE_COMMIT=1` (`:417`); `PRE_COMMIT_FROM_REF/TO_REF` and the
  legacy `PRE_COMMIT_ORIGIN/SOURCE` (note: `ORIGIN=from_ref`, `SOURCE=to_ref`)
  (`:386-392`); `PRE_COMMIT_COMMIT_MSG_SOURCE`, `PRE_COMMIT_COMMIT_OBJECT_NAME`
  (`:377-383`); `PRE_COMMIT_PRE_REBASE_UPSTREAM/BRANCH` (`:394-396`);
  `PRE_COMMIT_CHECKOUT_TYPE`, `PRE_COMMIT_IS_SQUASH_MERGE`,
  `PRE_COMMIT_REWRITE_COMMAND` (`:407-414`).

### 2.5 The staged-files stash (`staged_files_only.py`)

`with staged_files_only(store.directory)` (`run.py:419-421`). It composes two
context managers (`staged_files_only.py:107-112`):

1. `_intent_to_add_cleared` (`:35-47`): files from `git diff
   --diff-filter=A --name-only` (intent-to-add entries) are removed from the
   index with `git rm --cached` and re-added with `git add --intent-to-add`
   afterwards. This **mutates the index** during the run.
2. `_unstaged_changes_cleared(patch_dir)` (`:50-104`): `git write-tree`, then
   `git diff-index --binary --exit-code <tree>` (working tree vs index).
   - exit 0, or exit 1 with empty stdout (CRLF quirk) -> nothing to do
     (`:58-66`).
   - exit 1 with a diff: the diff is saved as a binary patch to
     `<patch_dir>/patch<unix-time>-<pid>` (`:68-75`), where `patch_dir` is the
     pre-commit **store directory** (`run.py:421`), then
     `git -c submodule.recurse=0 checkout -- .` discards the unstaged changes of
     tracked files (`:23`, `:81`). The hooks run. On exit (a `finally`,
     `:83-98`) the patch is re-applied with `git apply --whitespace=nowarn`
     (retrying with `core.autocrlf=false`, `:26-32`); if that fails because
     hooks modified the same hunks, it prints "Stashed changes conflicted with
     hook auto-fixes... Rolling back fixes..." and does `checkout -- .` again
     and re-applies the patch: **the hook auto-fixes are discarded** and the
     user's unstaged edit wins (`:88-96`).
   - other exit codes -> `FatalError` "pre-commit failed to diff" (`:99-104`).
- Untracked files are not touched by the stash (`checkout -- .` only affects
  tracked paths; `diff-index` only compares tracked paths) **(inference from
  the git commands used)**: hooks still see untracked files on disk.

Net effect: for tracked files, during the hooks the working tree equals the
index tree. The tree that `git write-tree` returns at `:52` is the content that
is about to be committed.

### 2.6 Which files a run considers

`_all_filenames` (`run.py:253-271`), in order:

1. hook stage in `post-checkout, post-commit, post-merge, post-rewrite,
   pre-rebase` -> no files (`:255-259`);
2. stage `prepare-commit-msg`/`commit-msg` -> the message file (`:260-261`);
3. `from_ref and to_ref` -> `git diff --name-only --no-ext-diff -z from...to`
   (three dots), falling back to two dots if there is no merge base
   (`git.py:158-167`);
4. `--files` -> exactly those (`:264-265`);
5. `--all-files` -> `git ls-files -z --deduplicate` (tracked files only)
   (`git.py:154-155`);
6. in a merge conflict (`MERGE_MSG` and `MERGE_HEAD` exist) -> the conflicted
   files plus the diff against HEAD/MERGE_HEAD (`:268-269`, `git.py:96-132`);
7. otherwise staged files: `git diff --staged --name-only -z
   --diff-filter=ACMRTUXB` (deleted files excluded) (`git.py:135-143`).

Note 3 outranks 4: if both `--files` and `--from-ref/--to-ref` are given the
refs win (`run.py:262-265`); the argparse mutual exclusion covers only
`--all-files` vs `--files` (`main.py:67-75`). The `Classifier` then drops
non-existent paths (`os.path.lexists`, `run.py:75`). **The file *contents* the
hooks read are always the working tree's, never `to_ref`'s** (for pre-push the
file list comes from the refs but nothing checks out `to_ref`;
`run.py:253-271` plus `staged_files_only.py` operate on the current checkout).

### 2.7 Per-hook execution, modification detection, exit code

`_run_hooks` (`run.py:282-322`): `prior_diff = git diff` (unstaged diff,
`_get_diff`, `:274-279`) before the loop; for each hook `_run_single_hook`
(`:142-235`):

- `hook.id in SKIP or hook.alias in SKIP` -> printed `Skipped`, exit 0
  (`:153-167`). `SKIP` is a comma-separated env var (`:129-131`). A skipped
  hook's environment is not installed (`:438-443`).
- no matching files and not `always_run` -> `(no files to check) Skipped`
  (`:168-183`).
- else: `pass_filenames: false` empties the file list (`:188-189`); the hook runs
  inside `language.in_env(...)` (`:192-201`) and the diff is taken again
  (`:203`). `files_modified = diff_before != diff_after` (`:206`). The hook is
  `Failed` when `retcode or files_modified` (`:208-213`) and prints
  "- files were modified by this hook" (`:227-228`).
  - The modification check compares the output of plain `git diff`
    (tracked, working tree vs index). A hook that only creates untracked files
    or rewrites files outside the repository (for example a `commit-msg` hook
    rewriting `.git/COMMIT_EDITMSG`) is **not** detected **(inference from
    `_get_diff`'s command)**.
  - Output of passing hooks is hidden unless `verbose` (global `-v` or the
    hook's `verbose`) (`:217`); on failure the id, exit code and combined
    output are printed (`:217-233`). `log_file` appends the output to that file
    in addition to stdout (`:232`, `output.py:14-29`).
- `fail_fast` (top-level `fail_fast`, hook-level `fail_fast`, or the `run
  --fail-fast` flag) stops *after* the first failing hook **of this invocation**
  (`:301-303`). Without it, all hooks run even after a failure, and later hooks
  see the files that earlier fixers modified.
- `--show-diff-on-failure` prints `git diff` at the end (`:304-320`).
- Return value: `files_modified or bool(retcode)` per hook (`:235`) OR-ed
  (`:300`), so `run` returns **0 or 1**. `hook_impl` ORs that with the legacy
  hook's code (`hook_impl.py:275`). Other exit codes: `FatalError`
  (invalid config, git failure, ...) -> 1; any other exception -> **3**; Ctrl-C
  -> 130 (`error_handler.py:70-81`); "No hook with id" -> 1 (`run.py:431-435`);
  a missing executable becomes retcode 1 with a message, not an exception
  (`util.py:97-108`, `xargs.py:346-348`). (Exit code 3 is also the code Sluice's
  git hook uses for "unverified" in its own skill; the collision is a
  coincidence of values to keep in mind when mapping exit codes,
  **inference from the Sluice skill text**.)

### 2.8 Environment, PATH, concurrency, xargs

- Each language's `in_env` patches `os.environ` for the duration of one hook
  run (`envcontext.py:32-62`, restored in `finally`). Python: `PATH` gets
  `<venv>/bin` prepended, `VIRTUAL_ENV` set, `PYTHONHOME` unset,
  `PIP_DISABLE_PIP_VERSION_CHECK=1` (`languages/python.py:55-60`, `:168-172`);
  node: `NODE_PATH` and `PATH` (`languages/node.py:56-57`); rust, go and others
  prepend their own `bin` (`languages/rust.py:53`, `languages/golang.py:73-82`).
  The executable is then resolved against the patched `PATH`
  (`xargs.py:346`, `parse_shebang.py:22-62`).
- Hook subprocesses inherit pre-commit's environment as-is. `no_git_env`
  (which strips `GIT_*` variables) is applied only to *clone/install*
  operations (`git.py:27-48`, `store.py:200`, `languages/golang.py:145`,
  `languages/node.py:107`), not to hook execution: grep of `no_git_env` shows no
  use in `run.py`/`lang_base.py`. So variables git exports while running a hook
  (for example `GIT_INDEX_FILE` for `commit -a`/`commit <paths>`, which the
  comment at `git.py:27-35` names as a source of bugs) reach the hooks
  **(inference about what git exports; the pass-through is in the code)**.
- Colour: default `auto` = `sys.stderr.isatty()` and `TERM != dumb`, or
  `PRE_COMMIT_COLOR` (`color.py:88-109`). When colour is on, hook processes run
  attached to a pty with stdin `/dev/null` (`util.py:162-200`); when off, stdin
  is a pipe closed at once (`util.py:81-83`, `communicate()` at `:107`). Hooks
  cannot read interactively either way.
- Working directory of hooks: the repository root (`main.py:188-189`);
  `unsupported_script` entries resolve relative to the hook repo prefix
  (`languages/unsupported_script.py:35-36`).
- **No shell**: `entry` goes through `shlex.split` (`lang_base.py:174-178`) and
  is executed directly; shell features require an explicit `bash -c '...'` entry.
  `entry: pre-commit hazmat ...` is rewritten to `python -m
  pre_commit.commands.hazmat` (`:176-177`); `hazmat` offers `cd`,
  `ignore-exit-code` and `n1` (`commands/hazmat.py:10-83`).
- **Concurrency** (`lang_base.py:135-171`, `xargs.py`): unless `require_serial`
  (or env `PRE_COMMIT_NO_CONCURRENCY`) the file list is shuffled with a fixed
  seed and split into partitions run in a thread pool of up to
  `len(os.sched_getaffinity(0))` workers (`xargs.py:222-234`, `:316-326`,
  `:371-373`). `max_args = max(4, ceil(n_files / concurrency))`
  (`xargs.py:282`); the command-line size limit is
  `min(SC_ARG_MAX - 2048 - env_size, 2**17)`, at least 4096 (`:245-249`).
  The reported return code is the one of largest absolute value across
  partitions; outputs are concatenated in partition order (`:375-378`). So one
  hook can use all CPUs of the machine, and the file partitioning changes the
  file list each process receives (relevant to hooks that are not
  partition-safe: that is what `require_serial: true` exists for).

## 3. Config semantics relevant to a runner

Schema: `clientlib.py:496-539` (root), `:465-490` (repo), `:439-464` (hooks).
Unknown keys only warn (`:520-533`, `:489`).

### 3.1 Repos

- `repo: local`: hooks come entirely from the config (`LOCAL_HOOK_DICT =
  MANIFEST_HOOK_DICT.items`, `:459-464`): `id`, `name`, `entry`, `language` are
  required (`:240-243`).
- `repo: meta`: only `check-hooks-apply`, `check-useless-excludes`, `identity`;
  `entry` cannot be overridden (`:376-438`); they run `python -m
  pre_commit.meta_hooks.<x>` with pre-commit's own interpreter (`:350-355`). They
  inspect the whole repository (`check_hooks_apply` uses `git.get_all_files()`
  and loads all hooks, `meta_hooks/check_hooks_apply.py:14-28`).
- `repo: <url>` + `rev`: `rev` is required, and the hook definitions
  (`name`, `entry`, `language`, `files`, `types`, ...) come from the manifest
  `.pre-commit-hooks.yaml` found in the checkout at `rev`
  (`repository.py:171-200`); the config overrides on top (`_hook`,
  `:109-144`). **The config alone therefore does not define a remote hook**:
  entry, language, types and default stages are only known after cloning.
  `rev` is passed to `git fetch origin <rev> --depth=1` / `git checkout
  FETCH_HEAD` with a full-clone fallback (`store.py:177-193`). A `rev` that
  looks mutable (no `.`, not hex) is warned about: "Mutable references are
  never updated after first install and are not supported" (`clientlib.py:294-310`).
- **`all_hooks()` clones every remote repo** of the config, even when only one
  hook id is selected: `run.py:426` calls `all_hooks(config, store)` over all
  repos (`repository.py:232-237`), and `_cloned_repository_hooks` calls
  `store.clone(...)` for each (`:177`, `:196`); the id filter is applied
  afterwards (`run.py:424-429`). The first run on a machine therefore needs
  network access to every remote repo of the config.
- Hook ids are not unique. `pre-commit run <id>` selects **all** hooks with
  `hook.id == id` or `hook.alias == id` (`run.py:424-429`), across repos.

### 3.2 `language`, environments, cost

21 languages (`all_languages.py:27-49`); `system` and `script` are accepted as
legacy names for `unsupported` / `unsupported_script`
(`clientlib.py:194-198`). Languages with `ENVIRONMENT_DIR = None` (no install):
`unsupported`, `unsupported_script`, `pygrep`, `fail`, `docker_image`; all others
install an environment: `conda coursier dart docker dotnet golang haskell julia
lua node perl python r ruby rust swift` (`ENVIRONMENT_DIR` grep).

- Cache root: `$PRE_COMMIT_HOME`, else `$XDG_CACHE_HOME/pre-commit`, else
  `~/.cache/pre-commit` (`store.py:25-36`); contents: an sqlite `db.db` mapping
  `(repo, ref)` to a directory `repoXXXXXXXX`, a `.lock` file, a `README`
  (`:59-101`, `:132-175`). Clones are keyed by `(repo + deps, rev)`
  (`:126-130`).
- Environment directory: `<clone>/<ENVIRONMENT_DIR>-<language_version>`
  (`lang_base.py:90-91`); readiness is the `.install_state_v1/v2` file plus
  `health_check` (`repository.py:25-62`). Python builds a virtualenv and runs
  `pip install . <additional_dependencies>` (`languages/python.py:211-224`).
- Local hooks with an environment live in a synthetic "local" repo directory
  keyed by `additional_dependencies` (`repository.py:152-159`, `store.py:212-215`);
  local hooks of `unsupported`/`pygrep`/`script`/`docker_image` use the current
  directory and install nothing (`repository.py:154-157`).
- Installation happens at the start of `run`, only for the selected,
  non-skipped hooks, under an exclusive file lock (`run.py:437-443`,
  `repository.py:214-229`, `store.py:103-109`). Output: "This may take a few
  minutes..." (`repository.py:66-68`). `language_version`/
  `additional_dependencies` on a no-environment language are a config error
  (`repository.py:126-142`).

### 3.3 Fields that change the set of files a hook sees (cache-key critical)

Applied in this order (`run.py:100-126`, `:151`):

1. Candidate set from section 2.6 (staged / from-to / `--files` / all /
   conflicted).
2. Top-level `files` (default `''`, matches all) and `exclude` (default `^$`)
   as `re.search` on each path (`clientlib.py:517-518`, `run.py:60-70`,
   `:112-126`). Slashes are normalised to `/` on Windows (`:123-124`).
3. Hook-level `files`/`exclude` (same regex semantics; the hook's `files`
   default comes from the manifest).
4. Type filter via `identify.tags_from_path` (`run.py:77-79`): `types`
   (default `[file]`, all required), `types_or` (any), `exclude_types`
   (`:81-98`, `clientlib.py:248-250`). `tags_from_path` inspects the file
   (extension, and shebang/content for extensionless files), so the result
   depends on the file's bytes and on the installed `identify` version
   (`clientlib.py:42-47`: "Try upgrading identify and pre-commit?") **(the
   content dependence is inference about the `identify` library, which is not
   in this checkout)**.
5. `pass_filenames: false` -> the hook runs with **no** file arguments but is
   still gated by steps 1-4: with an empty selection it is skipped unless
   `always_run: true` (`run.py:168`, `:188-189`). A `pass_filenames: false`
   hook thus depends on the *whole tree* for its result and on the *selected
   file set* for whether it runs.
6. `always_run: true` runs the hook even with an empty selection (`:168`).
7. `stages` (default `default_stages`, default all stages including `manual`,
   `clientlib.py:515`, `repository.py:123-124`): a hook is only considered when
   the requested `--hook-stage` is in its stages (`run.py:428`). Legacy names
   `commit`, `push`, `merge-commit` are translated (`clientlib.py:64-72`).
   `manual` is "not invoked by any installed git hook" (`:38`); run with
   `--hook-stage manual`.
7b. `args` are appended to the command line *before* the file names
    (`lang_base.py:174-178`); `entry` is the executable plus its fixed args.

Other fields: `require_serial` (section 2.8), `verbose`, `log_file`,
`language_version`, `additional_dependencies` (environment identity),
`fail_fast`, `minimum_pre_commit_version` (config load fails if the installed
pre-commit is older: `clientlib.py:50-60`, `:234-239`, `:500-505`), top-level
`default_language_version`, `default_install_hook_types`, `default_stages`,
`files`, `exclude`, `fail_fast`.

`ci:` is accepted and ignored: `cfgv.OptionalNoDefault('ci', check_type(dict))`
with the comment "do not warn about configuration for pre-commit.ci"
(`clientlib.py:537-538`). Nothing in pre-commit reads it; its meaning
(`skip:`, `autofix_prs`, ...) belongs to the hosted service (seen in real
configs, section 6) **(inference: not in this code)**.

### 3.4 Which hooks modify files, and can a per-hook runner reproduce them?

pre-commit has **no declaration** of whether a hook modifies files: there is no
`fixer` flag in the schema (`clientlib.py:230-265`). Modification is *detected*
after the fact (section 2.7). Whether a hook is a formatter can only be known
from its id/entry (heuristics) or by running it. In the real sample (section 6)
the common fixers are `trailing-whitespace`, `end-of-file-fixer`,
`mixed-line-ending`, `ruff-format`, `ruff --fix`, `black`, `prettier`,
`clang-format`, `isort`, and local hooks such as `eslint --fix`,
`cargo clippy --fix`, `prettier --write`.

What a re-implementation would have to match to reproduce a hook exactly:
config/manifest merge (needs clones of remote repos), `identify` type tags,
regex filtering, `default_stages`, the stash, language environments for 16
languages, the partitioning/shuffling and parallelism, `entry` shlex split,
`hazmat`, meta hooks, `SKIP`, the modification detection and the output
rules. A runner can safely reproduce only the subset where *entry, args,
files/exclude/types, stages and pass_filenames are all given in the local
config*; everything with `repo: <url>`, a non-trivial `language`, meta, hazmat
or env-dependent behaviour needs pre-commit's own interpretation.

## 4. Running a single hook id through pre-commit itself

### 4.1 Exact CLI

```
pre-commit run <hook-id-or-alias>            # main.py:65 positional 'hook'
    [-c/--config <file>]                     # main.py:50-55 (default .pre-commit-config.yaml)
    --hook-stage <stage>                     # choices: the 10 hook types + manual, plus the legacy
                                             #   aliases commit/push/merge-commit (transform_stage,
                                             #   main.py:84-90); default pre-commit
    ( --all-files | --files F... | --from-ref A --to-ref B )   # main.py:67-75, :97-117
    [--commit-msg-filename F] [--prepare-commit-message-source S] [--commit-object-name O]
    [--remote-name N --remote-url U --remote-branch B --local-branch L]   # env only: run.py:398-405
    [--checkout-type T] [--is-squash-merge V] [--rewrite-command C]
    [--pre-rebase-upstream U] [--pre-rebase-branch B] [--verbose] [--fail-fast]
    [--show-diff-on-failure] [--color auto|always|never]
```

(`--pre-rebase-upstream` and `--pre-rebase-branch` at `main.py:118-128`.)
`--from-ref`/`--to-ref` have the aliases `--source/-s` and `--origin/-o`
(`main.py:97-117`). There is **no dry-run and no "list files" option** among the
run options (`main.py:64-172`), so the file set a hook would receive cannot be
obtained from pre-commit without running the hook.

The exact equivalent of what the installed stub does for pre-push is the
`hook-impl` form: `pre-commit hook-impl --config=<cfg> --hook-type=pre-push --
<remote> <url>` with git's stdin (section 1.2, 2.3); it derives from/to itself.
`hook-impl` has no "only this hook id" option (`main.py:357-365`): the id filter
exists only on `run` (`args.hook`, `hook_impl.py:109` sets `hook=None`).

### 4.2 What it reproduces

For `pre-commit run <id> --hook-stage <stage> ...` all of this is pre-commit's
own code path, identical to a git-hook run **per hook**: config load and
validation including `minimum_pre_commit_version` (`run.py:423`), manifest
merge, `default_stages`, regex/type filtering, `identify`, env creation and
`PATH` patching, `entry` execution without a shell, `pass_filenames`/
`always_run` gating, xargs partitioning/concurrency, modification detection,
`SKIP`, the exported `PRE_COMMIT_*` variables and the output rules.

### 4.3 What differs from the real git-hook run

1. **Stash is per invocation, and it exists with refs.** `stash = not all_files
   and not files` (`run.py:344`): `--from-ref/--to-ref` stashes, `--files` and
   `--all-files` do not. When stashing, pre-commit does `git checkout -- .` on
   the checkout it runs in, and re-applies the patch afterwards
   (`staged_files_only.py:81-98`); with N hooks run as N invocations this
   happens N times instead of once, each time possibly conflicting with the
   previous invocation's auto-fixes. In a clean checkout (no unstaged diff)
   the stash is a no-op (`:58-60`) but the unmerged/unstaged-config checks still
   run (`run.py:347-358`).
2. **`--files`/`--all-files` bypass the config-unstaged and unmerged checks and
   the merge-conflict file source** (`run.py:344-358`, `:268-269`); `--files`
   passes paths verbatim (relative to the root after `main.py:191-193`). The
   hook's `PRE_COMMIT_FROM_REF`-style variables are only exported when both refs
   are given (`run.py:386-392`), so a hook that reads them forces the `--from-ref`
   form and therefore the stash.
3. **Modification detection scope**: `diff_before` is computed at the start of
   each `run` (`:294`), so hooks are judged individually; in a combined run a
   modification by hook A is "absorbed" into `prior_diff` and does not fail hook
   B (`:296-299`). Run separately, each invocation compares only itself
   (equivalent) but **order effects are lost**: hook B no longer sees A's fixes
   unless the invocations are chained on the same checkout in config order.
4. **`fail_fast` is meaningless** across invocations (`:301-303`).
5. **Network/clone cost on first use per machine** applies to every remote repo
   in the config, not just the requested hook (section 3.1), and the
   environment install runs under a global file lock (`store.py:103-109`).
6. **Pre-push file contents**: pre-commit never checks out `to_ref`; to run a
   pre-push-stage hook on the pushed commit Sluice would need that commit
   checked out; plain `pre-commit run <id> --hook-stage pre-push --from-ref A
   --to-ref B` reads the *current* working tree **(code facts, section 2.6;
   implication is inference)**.
7. **Exit code**: 0 or 1 from `run` (`:235`, `:300`), but `3`/`130` from the
   error handler (`error_handler.py:70-81`).
8. `colour`: when `--color auto` and stderr is not a tty (a Sluice job) the
   plain-pipe path is used (`color.py:104-109`, `util.py:201-202` fallback is
   Windows only); no pty.

### 4.4 Viable as a per-hook cached job?

From the code, yes, with limits:

- It avoids re-implementing the config interpreter, `identify`, env management
  and the partitioning. The unit is `pre-commit run <id>` (but see ids not
  unique: all hooks sharing the id run together, `run.py:424-429`).
- The wrapper must provide: a checkout where working tree == the tree being
  verified (so the stash has nothing to do, or pass `--files`); the same Python
  that has pre-commit; `PRE_COMMIT_HOME` reachable; network for the first clone;
  and handle the file list itself (when using `--files`, the wrapper must
  reproduce the selection of the *stage* and cannot ask pre-commit what it
  would select).
- Exit-code semantics are enough for pass/fail; "modified files" is expressed
  as exit 1 plus the hook output text "files were modified by this hook"
  (`run.py:227-228`); the modification itself is visible only as a working
  tree diff.

**Cache key inputs, from the code**: (a) hook id **and** repo/position (ids are
not unique; the full hook identity is `src`+`id`+the `_hook` merge result);
(b) the config file bytes (every top-level and hook key can change behaviour:
`files`, `exclude`, `default_stages`, `default_language_version`, `fail_fast`,
`minimum_pre_commit_version`), which also covers every `rev`; (c) for a remote
repo, the resolved commit the `rev` points to **(inference: for a branch or
moving tag the text of `rev` is not an identity; pre-commit itself says such
refs are never updated after first install, `clientlib.py:306`)**; (d)
`additional_dependencies` and `language_version` (part of the env identity,
`hook.py:277-283`); (e) the installed pre-commit version (`C.VERSION`, schema
and `identify` data) and the interpreter/OS for env-dependent hooks
(`repository.py:46-62` health check compares Python versions); (f) the stage and
the file selection: which files are *selected* depends on the candidate list
(staged / from-to / all) and on file *types* (content-based for some files);
(g) the content of the selected files and, for `pass_filenames: false`,
`system`/`script` hooks and meta hooks, the content of the whole tree (a
tree-hash key covers this); (h) the environment variables that hooks read
(`SKIP`, `PRE_COMMIT_*`, `GIT_*` passthrough, `PATH`), and external tools of
`language: system/unsupported` hooks, whose version is outside the config.

## 5. Delegation and drift

### 5.1 Handing the whole hook back, untouched

- The faithful form is `pre-commit hook-impl --config=<cfg> --hook-type=<type>
  -- <git args>` (section 1.2), fed the same stdin for pre-push (`hook_impl.py:31-34`).
  Without `--hook-dir` there is no legacy chaining (`:36-37`); with
  `--hook-dir <dir>` it runs `<dir>/<type>.legacy`.
- Or exec the stub itself if it still exists: the script is self-identifying
  (`is_our_script`, `install_uninstall.py:56-61`), takes `"$@"`, and does not
  read stdin by itself (the Python process does, for pre-push only,
  `hook_impl.py:31-34`).
- Interpreter: stub's `INSTALL_PYTHON` (a path embedded in the stub), else
  `pre-commit` on `PATH` (`hook-tmpl:13-20`). A wrapper that delegates by
  parsing the stub can read those lines (`install_uninstall.py:104-108` shows
  the exact generated format).

### 5.2 When pre-commit rewrites hooks

- `pre-commit install` (any type): overwrites its own stub unconditionally and
  moves a foreign file at that path into `.legacy` (`:64-86`). If Sluice's own
  hook file occupied `.git/hooks/pre-commit`, a later `pre-commit install`
  would treat it as foreign (no pre-commit hash, `:56-61`) and demote it to
  `pre-commit.legacy`; it would then run *before* pre-commit on every commit
  (`hook_impl.py:269`) and its non-zero exit would be OR-ed in (`:275`).
- `pre-commit uninstall`: removes only our stub and restores `.legacy`
  (`:149-161`).
- Re-running `install` rewrites `INSTALL_PYTHON` and `--config` from the current
  invocation (`:92-108`), so the stub's content drifts with the Python used.
- Something that runs `pre-commit install` automatically (documented only by
  convention, not in this code) can undo a Sluice redirection **(inference)**.
- `pre-commit autoupdate` rewrites `rev:` in the config
  (`commands/autoupdate.py`, not read in detail): a rev bump changes hook
  behaviour while the config bytes change too, so any key that hashes the
  config file bytes is invalidated by it.

### 5.3 Interplay with `core.hooksPath` set by another tool (Sluice)

- Sluice's per-clone `core.hooksPath` is local config; `pre-commit install`
  will refuse (`install_uninstall.py:123-128`, `git.py:180-182`) with the
  message in 1.3. This is a hard stop, not a warning; `-f` does not bypass it
  (the check precedes `overwrite` handling).
- With `core.hooksPath` pointing at Sluice, git does not execute pre-commit's
  `.git/hooks/*` stub (inference). pre-commit's runtime has no `core.hooksPath`
  logic, so Sluice can call `hook-impl`/`run` directly from its own hook file
  and pre-commit will behave the same as when invoked by its stub
  (`hook_impl.py` takes everything from arguments and stdin).
- To chain without re-implementing: Sluice's hook file for `<type>` executes
  `pre-commit hook-impl --config=<cfg> --hook-type=<type> -- "$@"` (or the stub
  at `<git-common-dir>/hooks/<type>` if present and ours) after Sluice has done
  its own cached steps; stdin must be forwarded for pre-push.
- Worktrees: hooks live in the common dir (`install_uninstall.py:47-53`);
  `core.hooksPath` is read via plain `git config` (the effective value for that
  worktree/clone).

## 7. Sluice context (read, not changed)

`sluice:crates/sluice-gate/src/init/hooks.rs` already reads
`.pre-commit-config.yaml` as text (`:354`, `Format::PreCommit` `:28`) and scans
only the hooks of `repo: local` entries (`FrameworkHook`, `:563-573`). From each
it takes `entry`, `stages`, `language`, `pass_filenames` and whether `args`
exist (`:600-625`). A hook with `args` is reported as manual, and one whose
`language` is not `system` is refused ("the hook's language is not system",
`scan_pre_commit`). `framework_stage` maps `stages` to `pre-commit` or
`pre-push` (`:695-707`). It does not read remote-repo hooks, `rev`,
`files`/`exclude`/`types`, `default_stages`, `always_run`, or the top-level keys.

## 8. Implications for the Sluice design

Facts first, then the constraint each one implies. Nothing here goes beyond
what the facts imply.

1. **A remote hook is not defined by the config.** Entry, language, default
   stages and types come from the manifest at `rev` (`repository.py:171-200`).
   -> "Understand the hook completely" can only be true for `repo: local`
   hooks (and `meta`/pygrep-style built-ins); every `repo: <url>` hook must be
   delegated to pre-commit. In the sample, 68 of 72 configs contain remote
   repos and only 4 are local-only.
2. **Selecting files is a non-trivial pipeline** (`files`, `exclude`, `types`
   via `identify`, `stages`, `pass_filenames`, `always_run`, `--from-ref`
   precedence, tracked/staged/conflicted sources; `run.py:60-126`, `:253-271`)
   and pre-commit offers no way to ask which files a hook would get (`main.py:64-172`).
   -> A Sluice-computed file list is only exact for hooks whose filters are
   fully understood; otherwise the cache key cannot include the "selected
   files", and the safe key is "whole tree + hook identity", with the run
   delegated to `pre-commit run <id>`.
3. **Fixers are not declared; pre-commit fails a hook that modified files**
   (`run.py:206-213`). -> A hook that exits 0 and left the diff unchanged is
   by pre-commit's own contract a pure check on that tree; a hook that modified
   files fails and is not a cacheable pass. "Modifying hooks first and
   uncached" is therefore a Sluice policy choice, not something pre-commit's
   semantics require; pre-commit's order is the config order, and later hooks
   see earlier fixers' changes (`run.py:295-303`), so reordering fixers ahead
   of checkers changes behaviour for hooks that depend on order. Untracked
   files created by a hook and edits outside the tree are not detected
   (`run.py:274-279`).
4. **The stash mutates the working tree and the index** (`checkout -- .`,
   `git rm --cached` of intent-to-add files; `staged_files_only.py:23`, `:35-47`,
   `:81`) whenever `run` is used without `--files`/`--all-files`, including
   `--from-ref/--to-ref`. -> Running `pre-commit run` inside the user's working
   tree conflicts with "never modify the user's index or working tree from
   product code"; it is compatible with a clean checkout of the tree being
   verified (where the stash is a no-op) or with the `--files`/`--all-files`
   forms, which skip it but also skip the unstaged-config/unmerged checks
   and the `PRE_COMMIT_FROM_REF` variables.
5. **`pre-commit run <id>` is a faithful per-hook executor** (section 4.2) but
   not free: it clones *all* remote repos of the config on first use
   (`run.py:426`, `repository.py:177`), installs environments under a global
   lock into `PRE_COMMIT_HOME` (`store.py:103-109`), spawns up to one process per
   CPU per hook (`xargs.py:222-234`), and its ids are not unique
   (`run.py:424-429`). -> Memory/CPU admission in Sluice must treat a
   delegated hook as a multi-process job; the cache directory and network
   access must be reachable from the job's sandbox; two hooks with the same id
   cannot be separated by id.
6. **The cache key for a delegated hook must include**: the full hook identity
   (repo + id + position), the config bytes, the resolved revision of each
   remote repo used, `additional_dependencies`/`language_version`, the pre-commit
   version, the stage, the tree (or the selected files plus, for
   `pass_filenames: false`/meta/`system` hooks, the whole tree), and the
   environment variables hooks read (section 4.4). Hooks with `language:
   system`/`unsupported`/`script` depend on external tool versions that are
   outside the config (`repository.py:154-157`, `lang_base.py:63-83` shows
   pre-commit itself treating home-directory shims specially); a key that
   ignores them can serve a stale pass.
7. **`hook-impl` is the exact entry point git uses and works without the stub**
   (`hook_impl.py:36-37`, `CHANGELOG.md:41-46`): arguments plus (for pre-push)
   stdin fully define the run, and `--config` is the only config pointer.
   -> Whole-hook delegation can be done by executing `hook-impl` with the same
   argv/stdin, after Sluice's own cached steps, with no dependence on the stub
   file or on `core.hooksPath`. The run result is 0 or 1 except 3 (unexpected
   error) and 130 (interrupt) (`error_handler.py:70-81`).
8. **`pre-commit install` refuses when any scope sets `core.hooksPath`**
   (`install_uninstall.py:123-128`, `git.py:180-182`) and, if Sluice's file
   occupies the stub's path, `install` demotes it to `.legacy` and runs it
   first (`:75-77`, `hook_impl.py:269-275`). -> With Sluice as the entry point
   through a local `core.hooksPath`, a later `pre-commit install` by the user or
   a tool fails loudly rather than silently displacing Sluice, but a Sluice
   hook placed in `.git/hooks` is displaced; the stub in `.git/hooks` stays
   inert while `core.hooksPath` is set (inference about git).
9. **pre-push ignores all but the first usable ref line and runs against the
   current working tree, not the pushed commit** (`hook_impl.py:134-171`,
   section 2.6). -> A Sluice pre-push step keyed on the pushed commit's tree
   is stricter than pre-commit's own behaviour for non-checked-out branches;
   exactly reproducing pre-commit means using the same first-line rule and the
   working-tree content, which only agree when the pushed ref is checked out.
10. **Real configs put the expensive work in a few shapes**: `language: system`
    hooks with `pass_filenames: false` and often `always_run: true`, entries
    wrapped in `bash -c 'cd <dir> && ...'`, bound to the default stage or to
    `pre-push` (section 6.2); formatters are overwhelmingly remote hooks
    (`ruff-format`, `black`, `prettier`, `trailing-whitespace`,
    `end-of-file-fixer`), present in 69 of 72 configs. -> The hooks that are
    heavy and simple enough to understand (local, `system`, no filenames) are
    the same ones a runner can wire as independent cached gates, while the
    fixers a runner would most need to run first are the remote ones it cannot
    interpret itself.
11. **Parsing limits are visible in the schema**: `minimum_pre_commit_version`
    fails config load on older pre-commit (`clientlib.py:55-60`); unknown keys
    only warn; `ci:` is ignored by pre-commit (`:537-538`); `default_stages`
    default includes `manual`. -> A text-level reader
    must treat any config key it does not know, any `minimum_pre_commit_version`
    above what it understands, and any non-default `default_stages`/`files`/
    `exclude` at top level as "delegate".
