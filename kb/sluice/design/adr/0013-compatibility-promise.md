# ADR-0013: Compatibility promise from 0.3.0

Status: accepted (2026-10-22). Design: [[sluice/design/compatibility.md]].
Plan: [[sluice/plan/alpha-plan.md]] task H3.

## Context

Formats were declared frozen at version 1 but nothing proved it, several
readers in released binaries are strict (markers with unknown fields are
deleted by 0.1.0/0.2.0, wire enums have no fallback, the daemon requires an
exact database schema version and has no migrations), and alpha users need
to know what may change.

## Decision

- The promise of section 1 of the design applies from 0.3.0: every
  interface keeps reading what released versions wrote; changes are
  additive only; a breaking change needs a new interface version, a
  migration path and one release of deprecation warnings. Whether old
  binaries read new data is documented per interface as a fact.
- Gaps fixed in 0.3.0 (design section 4): G4a (markers stop rejecting
  unknown fields; new marker fields stay forbidden until one release after
  that), G5 (`Unknown` fallbacks on the four wire enums), G1 (new gate
  options use new keys, never new types: `mode`, `paths`, `paths_ignore`),
  G2, G3, G6, G8, G10–G14 (fixtures, snapshots and tests), G7 (documented
  as a known limitation: a 0.2.0 binary cannot bind the short fallback
  socket path), G9 (a database migration framework in
  `sluice-gate-daemon/src/migrate.rs`: numbered, additive, transactional
  migrations applied on open and versioned by their own `sched_schema`
  table, a `sluice.db.bak-<version before>` copy before migrating an
  existing file, a test from a real 0.2.0 database; `schema.version` stays 1
  so 0.2.0 binaries keep opening the file; the queue tables keep
  `queue_schema` = 1, an older version is accepted and a newer one refused,
  nothing is migrated there).
- Golden files from the 0.1.0 and 0.2.0 release binaries live under
  `crates/*/tests/fixtures/compat/<release>/` (core, proto, daemon, queue
  and gate crates; regenerated by `scripts/compat/generate.sh`) and are
  never edited to make a test pass; the `v0.3.0` directories are added
  when 0.3.0 is released (not present yet).
- `docs/compatibility.md` is the user-facing version of this promise.

## Consequences

- Downgrades are supported only as far as the facts allow. 0.3.0 changes
  the database additively (`schema.version` stays 1), so 0.2.0 and 0.1.0
  binaries still open and write it. A future bump of `schema.version` would
  be refused by older binaries with an error naming the release that wrote
  the file (`meta` table); the `.bak-<version>` copy is the way back.
  `sluice update` does not warn about this.
- Every format change now costs a fixture and a test, by design.
